# 修复链实测报告（2026-10-04）

> 目的：量化修复链的有效性——在构造的损坏样本集上对照"带修复 vs 不带修复"。
> 三层共 21 例（工具层 9 / 输出层 8 / 检索层 4），零 API 成本（纯确定性实现）。
> 原始数据：`results/repair_benchmark.json`；复现：`experiments/repair_benchmark.py`。

---

## 一、结果

| 层 | 样本 | 不修复还原 | 修复后还原 | 提升 |
|---|---|---|---|---|
| 工具层 | 9 | 0 | **9** | +100.0% |
| 输出层 | 8 | 1 | **8** | +87.5% |
| 检索层 | 4 | 3 | **4** | +25.0% |
| **合计** | **21** | **4（19%）** | **21（100%）** | **+81.0%** |

**风暴抑制**：通过（前 3 次调用放行、第 4-5 次抑制）。

## 二、分层解读

### 工具层：0/9 → 9/9

三类故障全覆盖：嵌套参数（扁平化，含多层）、文本混入（从自由文本捞取调用）、
JSON 截断（括号与引号补全）。**不修复时的还原率为 0**——原始解析器对任一变形
均失败，这正是"工具调用在真实管线里会坏掉"的量化形态。

### 输出层：1/8 → 8/8

schema 违规的五类（类型错 / 缺默认字段 / 枚举大小写 / 多余字段 / 组合违规）
中，仅完全合规的 1 例原样可用；其余经本地修复（类型转换、补默认、枚举规范化、
字段剥离）全部转为可用。**三态语义严格**：缺必填与枚举外值判为拒绝（不猜测），
不可转类型同样拒绝。

### 检索层：3/4 → 4/4

低质量查询（停用词多、过泛）经放宽/收紧重写转为可用；全停用词查询明确拒绝
（无法重写）。提升幅度较小（+25%）的原因：该层 4 例中有 3 例本就"原样可用或
原样不可用"的边界情形，重写只在 1 例上产生实质改变。

## 三、口径与局限（如实标注）

1. **样本为设计目标内的故障类型**：对照的是"修复器是否实现了设计目标"，
   而非"野外泛化能力"——样本构造与修复器设计出自同源，**存在自造样本偏差**，
   100% 不应外推为"任意损坏均可修复"
2. **未覆盖设计外的故障**：语义错误（参数含义错）、多工具混合调用、
   非 JSON 格式的调用协议、恶意构造的畸形输入
3. **检索层的词表为示例规模**：同义扩展表与停用词表为演示用（各约 30 项），
   生产需替换为领域术语库
4. **各 pass 的单独贡献度未拆分测量**：本轮测的是"整链开关"效果，
   单项 pass 的边际贡献留作后续（需要更细的隔离样本）

## 四、结论

- 在设计覆盖的三类故障上，修复链把可用率从 **19% 提升到 100%**；
  提升最显著的是工具层（0 到 9）
- 拒绝路径（14 例单测中的 3 类拒绝场景）与修复路径同等重要：
  无法修复时明确拒绝，避免坏参数进入执行
- 修复链的价值定位：**降低重试率**（本地修复替代一次模型往返），
  其成本为纯确定性计算（零 API 调用）
